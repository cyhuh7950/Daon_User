# Daon 개발 Subagent 인계

## 개요

Daon 개발 작업에서 어울1의 설계 책임을 유지하면서 어울2의 구현 결과를 한 메인 워크플로로 회수하라. 요구사항 변경이나 최종 완료 판단을 자동화하지 마라.

## 1. 시작 조건 확인

1. 저장소 루트의 `AGENTS.md`를 읽고 역할과 승인 경계를 적용하라.
2. 승인된 상세 설계서와 작업계획서의 경로와 버전을 확인하라.
3. 두 문서 중 하나가 없거나 승인 상태가 불명확하면 코드를 수정하지 말고 `BLOCKED`로 보고하라.
4. 현재 작업공간, Git 상태, 관련 변경 파일과 실행 가능한 검증 명령을 확인하라.
5. 동일 범위를 수정 중인 Agent가 없는지 확인하라.

`BLOCKED`와 `INCOMPLETE`는 정식 실패보고로 계산하지 마라.

## 2. 작업 패킷 작성

어울2에게 다음 항목을 빠짐없이 전달하라.

- `issue_id`: 같은 문제의 재작업에서 유지할 식별자
- 목표와 사용자 관점의 완료 조건
- 승인된 상세 설계서와 작업계획서 전체 경로 및 버전
- 이번 작업 범위와 제외 범위
- 허용된 변경 파일 또는 모듈
- 유지해야 하는 기존 기능과 외부 동작
- 요구사항·API·데이터·보안·배포 승인 경계
- 수행할 테스트와 필요한 완료 증거
- 현재 Git diff, 선행 변경, 알려진 위험과 미해결 사항
- 단계별 진행 복구 기록 경로와 갱신 시점·필수 필드

요약만 전달하지 말고 승인 문서 전체를 읽게 하라. 설계자의 판단 과정이 문서만으로 재현된다고 가정하지 말고, 구현 중 발견 사항을 어울1에게 되돌리는 경로를 명시하라.

## 3. 개발 Subagent 실행

1. 프로젝트 Custom Agent `daon-developer`를 어울2로 한 명만 실행하라.
2. 어울2가 종료할 때까지 기다리고 결과보고와 변경 상태를 수집하라.
3. 실패보고 1·2회에는 가능하면 같은 어울2에게 갱신한 작업지시를 전달하라.
4. 현재 실행 환경에서 Custom Agent 이름을 직접 선택할 수 없으면 개발자 지침과 작업 패킷을 그대로 제공한 단일 Subagent를 사용하고 그 사실을 결과에 남겨라.
5. 어울2가 쓰는 동안 어울1이나 다른 Agent가 같은 작업 범위를 수정하지 못하게 하라.

## 4. 결과 계약 적용

모든 종료 결과에 다음 필드를 요구하라.

`status | issue_id | 수행한 작업 | 생성·변경한 결과 | 테스트 결과 | 미해결 사항 | 다음으로 필요한 판단`

상태를 다음과 같이 판정하라.

- `COMPLETED`: 필수 산출물, 변경 파일, 완료 조건별 근거와 테스트 결과가 모두 있다.
- `FAILURE_REPORT`: 동일 문제를 식별할 `issue_id`, 실패 단계와 확인 원인, 오류·테스트·관련 코드 증거, 현재 변경 파일과 남은 작업, 어울1에게 필요한 구체적 기술 판단을 모두 포함한다.
- `INCOMPLETE`: 결과보고가 미완성이거나 예기치 않게 종료됐다. 실패 횟수를 유지하고 같은 Agent를 재개하거나 새 Agent가 현재 상태부터 이어받게 한다.
- `BLOCKED`: 권한, 환경 또는 신산님의 결정이 필요하다. 원인을 분류하고 필요한 결정만 상위로 요청한다.

형식만 `FAILURE_REPORT`이고 필수 근거가 없으면 실패 횟수에 추가하지 말고 `INCOMPLETE` 또는 `BLOCKED`로 재분류하라. `Done` 표시만으로 `COMPLETED`를 인정하지 마라.

## 5. 결과별 후속 처리

### COMPLETED

1. 작업계획의 완료 조건과 변경 근거를 대조하라.
2. 정적 확인, 빌드, 자동 테스트, 실제 화면 또는 운영 검증을 구분하라.
3. 충족하면 최신 설계 문서와 최종 diff를 외부 독립 검증자에게 현재 방식으로 전달하라.
4. 독립 검증 결과까지 수집한 뒤 신산님에게 최종 완료 판단을 요청하라.

### FAILURE_REPORT 1회

1. 원인과 증거를 검토하라.
2. 승인 범위 안에서 보완 지시 또는 새로운 기술 방향을 정하라.
3. 작업지시를 갱신해 동일 어울2에게 재작업을 전달하라.

### FAILURE_REPORT 2회

1. 설계 가정과 실제 코드 구조의 충돌을 다시 검토하라.
2. 필요하면 설계서·작업계획·결정 기록을 먼저 갱신하라.
3. 갱신된 전체 문서와 작업지시를 동일 어울2에게 전달하라.

### 동일 작업지시서 FAILURE_REPORT·INCOMPLETE 합계 3회 또는 유효한 FAILURE_REPORT 3회

1. 동일 작업지시서의 원보고를 확인하고, 유효한 실패 횟수와 `INCOMPLETE`를 구분해 Attempt Ledger에 기록하라.
2. 어울2의 추가 쓰기 작업을 중지하라.
3. 원보고, 현재 Git diff, 변경 파일, 테스트 결과와 남은 작업을 수집하라.
4. 신산님에게 현재 상태와 어울1 직접 구현 필요성을 보고하고 결정을 기다려라.
5. 신산님이 직접 구현을 승인한 경우에만 `DIRECT_IMPLEMENTATION` 상태를 명시적으로 선언하라.
6. 구현 방법이 달라지면 관련 설계서·작업계획·결정 기록을 먼저 갱신하라.
7. 어울1이 현재 상태를 인수해 직접 구현하라.
8. 최신 문서와 최종 diff를 외부 독립 검증자에게 전달하라.

개발자와 설계자가 동시에 쓰는 방식으로 인수하지 마라.

### INCOMPLETE

1. 실패 횟수를 올리지 마라.
2. 현재 변경 파일, 진행 복구 기록, 마지막 성공 단계와 남은 작업을 회수하라.
3. 동일 작업지시서의 의무 보고 누적 횟수에는 포함하되 유효한 실패 횟수와 혼합하지 마라.
4. 합계 3회 미만이면 동일 어울2를 재개하라. 재개할 수 없으면 새 어울2에게 현재 상태와 원래 작업 패킷을 모두 전달하라.

### BLOCKED

1. 실패 횟수를 올리지 마라.
2. 권한·환경·설계 판단·사용자 승인 중 어느 종류인지 분류하라.
3. 승인 경계 안의 기술 문제는 어울1이 판단하고, 범위·요구사항·공개 API·데이터·보안·중요 위험 변경만 신산님에게 요청하라.

## 6. 메인 대화 보고

신산님에게 다음만 간결하게 정리하라.

- 현재 상태와 `issue_id`
- 완료된 변경과 검증 근거
- 실패보고 누적 횟수 또는 중단 복구 상태
- 남은 위험과 필요한 승인
- 다음 실행 주체가 어울2인지 어울1인지
- 테스트 계획이 지정한 웨이브 도달 여부와 신산님의 Go/No-Go 필요 여부

신산님이 설계자와 개발자 사이의 결과를 직접 복사해 전달하도록 요구하지 마라.

## 7. 자동화 경계 유지

- 이 Skill은 결과 전달, 대기, 수집, 상태 분류, 재작업과 인계만 수행하라.
- 기능 범위, 요구사항, 설계 승인, 최종 완료 판단, 파괴적 작업, 외부 배포와 예외 수용을 자동화하지 마라.
- 외부 독립 검증자를 Codex Subagent로 가장하거나 자동 연결됐다고 주장하지 마라.
- 기계적으로 판별할 조건이 실제 작업에서 안정되기 전에는 Hook을 추가하지 마라.
- 여러 사용자에게 배포할 필요가 확인되기 전에는 Plugin으로 포장하지 마라.

## 8. 실행 종료 점검

다음을 모두 확인하고 메인 워크플로를 종료하라.

- 신산님이 어울1과 어울2 사이의 결과를 직접 복사해 전달하지 않았다.
- 어울1이 전체 설계 맥락과 기술적 재작업 지시를 계속 소유했다.
- 어울2가 중단 시 원인, 현재 상태와 남은 작업을 남겼다.
- 예기치 않은 중단이 `FAILURE_REPORT`로 잘못 누적되지 않았다.
- 동일 작업지시서의 미완료·실패 합계 3회 또는 동일 문제의 세 번째 유효한 실패보고에서 어울2 중지, 신산님 보고·결정, 승인 후 어울1 인수가 순서대로 실행됐다.
- 어울1과 어울2가 동시에 같은 작업 범위를 수정하지 않았다.
- 독립 검증은 최신 설계 문서와 최종 변경사항을 기준으로 수행됐다.
