## 질의 목록

### Q1 — "중요 충돌"의 판정 기준

- **근거**: §7.4 "해결되지 않은 중요 충돌은 검토 상태로 전환한다."
- **미정의**: '중요'를 누가/무엇으로 판정하는가. 자동 규칙(권위 tier 차이·상충 강도 임계값 등)인가, 사용자·검토자 지정인가.
- **테스트 영향**: TS-KNW-033은 "중요 충돌 상황 유도" 후 검토 전환을 기대하나, 판정 기준이 없어 어떤 입력이 '중요'인지 구성할 수 없다.
- **제안 선택지**: (a) 상위-하위 tier 간 상충은 자동 '중요' / (b) 사용자가 충돌 항목을 '중요'로 표시 / (c) 둘의 조합.

### Q2 — 사용자 가중치 값 범위·척도·기본값

- **근거**: §7.3 `within_tier_score = normalized_relevance × user_weight × source_quality × freshness`
- **미정의**: `user_weight`의 값 범위(예: 0.1~10), 척도(연속/단계값), 기본값, 유형·그룹·개별 3단계가 충돌할 때 우선순위.
- **테스트 영향**: TS-KNW-021(3단계 조합)·TS-KNW-024(경계값)의 기대 결과를 확정할 수 없다.
- **제안 선택지**: 범위·기본값을 M0(R1-D) 정책값으로 확정하고, 3단계 충돌은 "개별 > 그룹 > 유형" 최근접 우선 규칙 명시.

### Q3 — 비용 한도 초과 시 종료 상태

- **근거**: §10.4 RoutingContext에 "정책 버전·기한·비용 한도" 포함. 그러나 §10.5 종료 상태 목록에 비용 초과 항목이 없음.
- **미정의**: 실행 중 비용 한도 도달 시 종료 상태가 `policy_blocked`인지, 별도 코드(예: `COST_LIMIT_EXCEEDED`)인지, 재시도 가능 여부.
- **테스트 영향**: TS-MDL-030 기대 결과 미확정.
- **제안 선택지**: 별도 종료 코드 신설 + 재시도 불가로 고정하고 §10.5·§18.2에 추가.

### Q7 — 모바일 "간단 편집" 허용 범위

- **근거**: §4.2 "업무 Studio 편집 … 간단한 수정·검토 중심".
- **미정의**: 모바일 간단 편집이 텍스트 수정만인지, 표 Cell·구조·근거 연결 편집을 포함하는지.
- **테스트 영향**: TS-STU-060 허용 범위 검증 기준 부재.
- **제안 선택지**: 허용 편집 유형을 화이트리스트로 명시(예: 텍스트 인라인 수정·검토 코멘트만, 구조·표·재생성은 Web/Windows).

### Q8 — "민감 작업"의 구체 목록

- **근거**: §14.4 "민감 작업의 추가 인증".
- **미정의**: 추가 인증을 요구하는 민감 작업의 목록.
- **테스트 영향**: TS-SEC-084는 "민감 작업 수행" 후 추가 인증을 기대하나 대상 작업이 불명확.
- **제안 선택지**: 최소 목록 명시 — 외부 전달, 생산 지식 등록, 영역 이동(Local→Cloud), 조직 정책 변경, 장치 철회 등.

### N1 — 음성/ASR 처리 sub-state 미모델링 (신규)

- **근거**: §18.1 `processing(vision_llm_understanding → parser_ocr_validation → evidence_reconciliation)` vs §8.2 파이프라인의 "오디오 음성 인식과 시간 구간 생성" 단계.
- **미정의**: §18.1의 처리 sub-state는 문서 중심이며 오디오 전용 Source(M4A/WAV/MP3)가 거치는 sub-state를 정의하지 않는다. 오디오는 `vision_llm_understanding`이 아니라 `speech_to_text`를 거친다.
- **테스트 영향**: TS-SRC-030~033(음성 전사·계보)의 상태 추적 기준이 없다. 오디오 Source가 어떤 sub-state를 지나 `ready`가 되는지 판정 불가.
- **제안 선택지**: §18.1에 오디오 처리 분기 sub-state(예: `transcribing → transcript_review → evidence_reconciliation`) 추가, 또는 Modality별 sub-state 표로 분리.

### N2 — `waiting_model` 재시도 촉발 조건 미정의 (신규)

- **근거**: §8.2·§10.5·§18.1 — 정책 허용 후보의 Runtime 실패가 소진되면 Source `waiting_model`, ProcessingRun `failed/NO_AVAILABLE_UNDERSTANDING_MODEL`.
- **미정의**: `waiting_model` Source의 재처리를 누가/언제 촉발하는가. 모델 복구를 자동 감지해 재시도하는가, 사용자·운영자 수동 재처리인가, 촉발 조건(주기·이벤트)이 무엇인가.
- **테스트 영향**: TS-SRC-017B는 "재시도 가능성 표시"를 기대하나, 재시도 트리거 메커니즘이 없어 재처리→`ready` 전환 경로를 검증할 수 없다.
- **제안 선택지**: (a) 모델 Deployment `ready` 복귀 이벤트에 자동 재큐 / (b) 운영 화면의 수동 재처리 / (c) 둘 다 지원하고 기본은 자동.

### N3 — 권한 변경 후 과거 결과 재검증 규칙의 계승 여부 (신규)

- **근거**: 구 독립 설계서(`HIST-001`, SUPERSEDED)의 "권한 변경 시 과거 결과는 보존하되 원문 접근·재실행을 현재 권한으로 재검증".
- **미정의**: 개정 정본 §14에 이 규칙이 명시적으로 계승됐는지 불명확. 문서 해석 원칙 §0-2에 따라 "명시 계승되지 않으면 적용하지 않는다"이므로, 계승 명시가 없으면 이 동작은 요구사항이 아니다.
- **테스트 영향**: TS-SEC-015의 근거 조항이 불확실. 계승 여부에 따라 시나리오 유지/삭제가 갈린다.
- **제안 선택지**: 계승이 맞으면 §14에 명문화, 아니면 TS-SEC-015를 범위에서 제외.
